# 라이브뷰 안정화 문제해결 기록

> 문제 발견 → 방법 탐색 → 해결 → 재검증의 반복으로 확인한 내용

## 기록 개요

| 항목 | 내용 |
|---|---|
| 대상 | Nikon D810 · Opal DD 서버 · WebSocket/Web UI · Flutter Android 앱 · Samsung S10 |
| 검증 환경 | 인터넷 단절 상태의 로컬 LAN, Opal `192.168.8.1`, S10 무선 ADB |
| 기록 기준 | 2026-08-02 현재 배포본과 실기 검증 결과 |
| 핵심 결론 | 반복 프레임을 제거한 뒤에도 약 60 FPS급 고유 프레임 표시를 확인했으나, 원본 프레임 무손실은 별도 목표로 남음 |

> **결론 요약**  
> 현재 라이브뷰는 마지막 프레임을 재활용해 60을 만드는 구조가 제거되었다. 최초 고유 프레임 벤치마크는 `59.953 FPS`, `repeatedFrames=0`이었다. 다만 측정값은 구간에 따라 57~59 FPS로 변동하므로, 앞으로는 **출력 FPS**와 **원본 수신 FPS**를 구분해 기록해야 한다.

## 1. 출발점: 인터넷이 끊기면 무엇이 달라지는가

출사 환경에서는 인터넷이 없어도 카메라 제어가 계속되어야 했다. 초기 테스트에서 셔터와 AF는 동작했지만 라이브뷰가 들어오지 않았고, STOP도 먹통처럼 보였다. 개발 환경에서는 인터넷이 연결되어 있어 문제가 드러나지 않았기 때문에 네트워크 자체가 원인인지, 종료·재연결 경로의 경쟁 상태인지 분리해야 했다.

- 로컬 LAN 경로와 인터넷 의존 경로를 분리했다. 인터넷 없이도 S10 ↔ Opal ↔ D810의 로컬 통신은 가능해야 한다.
- Tailscale은 상시 경로가 아니라 필요 시 수동 시작하는 선택적 관리 경로로 정리했다.
- 웹 UI와 앱 모두 같은 DD 서버와 라이브 세션을 사용하므로, 로그는 접속 방식이 아니라 서버·브리지·클라이언트 공통 경로에 남아야 한다.

**판단**  
인터넷 단절은 직접적인 영상 데이터 경로의 필수 조건이 아니었다. 대신 인터넷이 있던 개발 환경에서는 경쟁·재연결·종료 타이밍이 덜 발생해 잠복 버그가 드러나지 않았을 가능성이 컸다.

## 2. 첫 번째 핵심 문제: `live-off`가 생산자를 확실히 끝내지 못함

문제의 중심은 `live-off` 자체가 아니라 백그라운드 프레임 생산자의 생명주기였다. 화면에서 라이브를 끄더라도 생산자가 계속 돌거나, 반대로 생산자가 중간에 멈춘 뒤 클라이언트가 마지막 상태를 붙잡고 있으면 STOP과 라이브뷰 상태가 서로 다르게 보일 수 있었다.

해결 루프는 다음과 같았다.

1. 증상을 재현하고 앱·웹·서버 로그를 함께 비교했다. 셔터/AF와 라이브뷰/STOP을 분리해 각각의 경로를 확인했다.
2. DD 서버부터 bridge, WebSocket, Web UI, Flutter 앱까지 전체 경로를 나눠 어느 단계가 살아 있는지 확인했다.
3. `live-off` 시 백그라운드 생산자 종료, WebSocket 종료, 화면 FPS 초기화를 하나의 종료 경로로 맞췄다.
4. STOP 후 서버 상태가 `liveView=false`인지, LIVE 재시작 후 `frameAge`가 짧고 `frameFailures=0`인지 실기에서 확인했다.

## 3. 두 번째 문제: 24 FPS로 보이던 라이브뷰

인터넷 단절 뒤 나타난 24 FPS 현상은 단순히 카메라가 24 FPS로 내려간 것이 아니었다. 직접 스트림이 실패하면 파일 폴링으로 떨어지는 경로, 중복 bridge가 서로 다른 스트림 포트를 잡는 상황, WebView의 JPEG 디코드와 렌더가 직렬화되는 상황이 겹쳐 있었다.

| 관찰 | 원인 후보 | 확인·조치 |
|---|---|---|
| 직접 스트림 종료 후 화면 정지 | `d810ws`가 실패 시 연결을 닫고 종료 | 실패 시 파일 fallback 루프로 전환 |
| 같은 서버에 bridge가 둘 존재 | 기본 bridge와 v21 bridge의 스트림 포트 충돌 | 중복 bridge 제거, v21 포트만 유지 |
| 폴링이 느림 | 기본 33ms 주기 | `D810D_WS_POLL_MS=1`로 조정 |
| 앱 렌더가 밀림 | JPEG decode·렌더·표시가 한 흐름으로 묶임 | 수신·디코드·렌더 분리, 큐와 WebGL 경로 정리 |

**해결 루프**  
한 번에 전체를 바꾸지 않고 `서버 단독 상태 → WebSocket 프레임 → WebView 렌더 → Flutter 표시` 순서로 좁혀 갔다. 각 단계에서 FPS와 `frameId`를 따로 확인한 것이 원인 분리에 중요했다.

## 4. 세 번째 문제: 60 FPS처럼 보이지만 실제로는 반복 프레임

초기 최적화 뒤 화면 FPS는 59.9에 가까워졌지만, 검증 과정에서 STOP 후에도 FPS가 60으로 남는 반례가 발견됐다. 렌더 타이머가 새 프레임이 없을 때 마지막 텍스처를 다시 그리는 구조였기 때문이다. 이 수치는 화면 출력 주기이지, 카메라에서 새 고유 프레임이 들어온 속도가 아니었다.

| 잘못된 가정 | 반례 | 수정 방향 |
|---|---|---|
| 화면 FPS 60이면 입력도 60 | STOP 후에도 FPS가 60으로 유지 | 입력 프레임과 출력 프레임을 분리 |
| 렌더 타이머가 계속 돌면 안정적 | 마지막 텍스처 재출력으로 숫자만 유지 | 새 디코딩 프레임이 있을 때만 렌더 |
| 프레임 수만 세면 됨 | 같은 `frameId` 재수신 가능 | `frameId` 중복·역행을 큐에서 차단 |

## 5. 최종 해결: 고유 프레임 전용 렌더링

다음과 같이 구현을 수정했다.

1. 동일하거나 이전 `frameId`는 큐에 넣지 않는다.
2. `decodedQueue`가 비었을 때 마지막 텍스처를 재활용하는 분기를 삭제한다.
3. FPS 집계는 실제 렌더 완료된 고유 프레임만 포함한다.
4. STOP 시 렌더 타이머를 끄는 동시에 FPS를 즉시 0으로 보고한다.
5. 빌드 성공 후 S10에 배포하고, 초기 60프레임의 `frameId`, `repeatedFrames`, `frameIdGaps`를 확인한다.

### 검증 결과

- 최초 고유 프레임 벤치마크: **59.953 FPS**
- `repeatedFrames=0`
- 표시된 `frameId`는 증가
- 마지막 프레임 재활용 없음
- 일부 원본 프레임은 큐가 밀릴 때 건너뛸 수 있음

따라서 **고유 프레임 표시**와 **모든 원본 프레임 무손실 표시**는 구분해야 한다.

## 6. 10분 실사용 안정성 검증에서 배운 것

첫 번째 10분 시도는 300초에서 S10 화면 자동 꺼짐으로 앱이 전면에서 내려가 무효 처리했다. 이 경험으로 테스트 조건 자체도 검증 대상임을 확인했다. 화면 꺼짐 시간을 시험 중에만 연장하고 원래 값으로 복원한 두 번째 회차를 유효한 실사용 시험으로 기록했다.

| 항목 | 유효 회차 결과 |
|---|---|
| 시간 | 10분, 60초 간격 11개 표본 |
| 앱 전면 상태 | 11/11 유지 |
| 표시 FPS | 각 표본 60.0으로 관찰 |
| S10 배터리 온도 | 38.5°C → 37.6°C, 상승 없음 |
| 서버 상태 | 시험 종료 시 `frameAge=99ms`, `frameFailures=0` |
| 브리지 오류 | 시험 시간대 신규 오류 없음 |
| STOP/LIVE 재검증 | STOP `liveView=false`, LIVE `liveView=true`, `frameAge=8ms` |

> **주의**  
> 이 10분 회차의 FPS 창은 당시 반복 재출력 로직이 포함된 버전이었다. 따라서 ‘출력 루프와 연결의 안정성’ 증거로는 유효하지만, 고유 입력 프레임 10분 연속 검증으로 과장해서는 안 된다. 고유 프레임 기준은 이후 수정본의 `frameId`·`repeatedFrames` 벤치마크로 별도 확인했다.

## 7. 현재 상태와 다음 검증 기준

현재 라이브뷰는 재활용 프레임 없이 고유 `frameId`를 가진 프레임만 표시한다. 실기에서 60 FPS급 고유 프레임을 확인했지만, 측정값은 초기화·렌더 타이밍에 따라 57~59 FPS로 변동했다. 따라서 ‘60이라는 표시’보다 다음 네 가지를 함께 기록하는 것이 새로운 기준이다.

- 고유 표시 FPS: `repeatedFrames=0`인지 확인
- 프레임 연속성: `frameId` 증가와 `frameIdGaps` 확인
- 생산자 상태: `frameAgeMs`, `frameFailures`, `reconnectCount` 확인
- 종료·재시작: STOP `liveView=false`, LIVE 후 `frameAgeMs` 회복 확인

**남은 과제**  
현재는 표시 프레임의 중복을 제거한 상태다. 다음 안정화 단계는 원본 프레임 생산 FPS와 앱 표시 FPS를 서버·앱에서 각각 공개하고, 큐에서 건너뛴 원본 프레임까지 포함한 10분 고유 프레임 시험을 별도 자동화하는 것이다.

## 부록. 핵심 용어

| 용어 | 의미 |
|---|---|
| 고유 프레임 | 이전에 표시한 것과 다른 `frameId`를 가진 새 카메라 프레임 |
| 반복 프레임 | 새 입력 없이 마지막 텍스처를 다시 그린 화면 |
| `frameIdGaps` | 수신·렌더하지 못하고 건너뛴 `frameId` 개수 |
| `frameFailures` | DD 서버의 백그라운드 프레임 생산 실패 누적값 |
| `frameAgeMs` | 마지막 정상 프레임이 생성된 뒤 경과한 시간 |
