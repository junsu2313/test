# 5차 프레임 최적화 — 0x9203 USB 읽기와 라이브뷰 경로

> 상태: **FROZEN BASELINE**
>
> 기준일: 2026-07-28  
> 이 버전을 D810 라이브뷰의 최종 성능 기준선으로 사용한다.

## 결론

- 실제 Opal과 Nikon D810에서 수정 전·단계별 수정 후·최종 배포 후를 측정했다.
- 최종 USB bulk 요청 크기는 `32768`바이트로 선택했다.
- 4차 기준 대비 UI 평균 FPS는 `28.07 → 55.94`로 `99.3%` 증가했다.
- 전체 지연 평균은 `28.04 → 14.22 ms`로 `49.3%` 감소했다.
- 전체 지연 p95는 `31 → 15 ms`로 `51.6%` 감소했다.
- 최종 스케줄링 보완으로 프레임 사이 request gap 평균을 `5.87 → 3.88 ms`로 줄였다.
- 최종 상태는 Ready, LIVE off이며 외부 노출과 Tailscale SSH는 사용하지 않았다.

## 동결 기준

- UI FPS 평균: `55.94 fps`
- UI FPS p10 / p50 / p95 / 최대: `52.7 / 56.5 / 58.1 / 58.5 fps`
- 실생산 FPS: `55.72 fps`
- 전체 지연 평균 / p50 / p95 / 최대: `14.22 / 14 / 15 / 15 ms`
- request gap 평균: `3.88 ms`
- 시스템 CPU busy: `39.44%`
- Bridge / WebSocket CPU: `14.23% / 8.40%`
- USB bulk 요청: `32768`바이트
- 이후 라이브뷰 경로 변경은 이 수치와 동일 조건으로 전후 측정하고, 성능 또는 안정성 회귀가 있으면 적용하지 않는다.

## 프레임 수 해석

- 이번 결과는 순간 최대치가 아니라 50개 UI 표본에서 평균 `55.94 fps`, p50 `56.5 fps`를 기록한 **56 fps급 실효 라이브뷰 처리율**이다.
- `0x9203` 경로가 기존의 30 fps 추정치를 넘어섰으므로, 종전 한계의 상당 부분은 카메라보다 USB 요청·파싱·전달 루프에 있었다.
- 현재 결과를 바탕으로 D810 내부 라이브뷰가 60 fps급으로 생성될 가능성을 기대한다.

## 적용 내용

1. ddserver의 0x9203 USB 읽기 버퍼를 재사용하고 bulk 요청 크기를 설정 가능하게 변경
2. USB endpoint의 512바이트 packet 크기와 애플리케이션 read 요청 크기를 분리
3. bridge에서 Nikon 384바이트 헤더와 JPEG를 한 번에 직접 분리
4. bridge→WebSocket 메타데이터를 52바이트 바이너리 헤더로 전달
5. JPEG 본문 복사와 캐시 중복 쓰기를 줄이고 TCP 지연 옵션 적용
6. 세로·가로 UI가 동일한 바이너리 메타데이터와 프레임 경로를 사용
7. 직접 스트리밍 중 매 프레임 끝에 실행되던 고정 2ms idle sleep 제거

| bulk 요청 | UI FPS 평균 | FPS p50 | 지연 평균 | 지연 p95 | USB reads/frame | USB total 평균 / p95 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 B | 33.02 | 33.6 | 24.12 ms | 26 ms | 약 65 | 23.85 / 34.67 ms |
| 4 KiB | 42.52 | 42.9 | 17.48 ms | 19 ms | 약 10 | 추적 표본 10.08–18.56 ms |
| 16 KiB | 47.59 | 47.6 | 15.00 ms | 15 ms | 4 | 9.28 / 15.12 ms |
| 32 KiB | 49.03 | 49.0 | 14.30 ms | 15 ms | 3 | 8.85 / 14.61 ms |
| 64 KiB | 49.13 | 49.0 | 14.45 ms | 15 ms | 3 | 8.97 / 15.29 ms |

64 KiB는 32 KiB보다 프레임 이득이 측정 변동 범위에 불과했고 USB 평균·꼬리 지연은 오히려 나빠졌다. 따라서 더 작은 메모리 요청으로 같은 성능과 더 나은 안정성을 보인 32 KiB를 선택했다.

## 배포와 검증

- Linux 빌드 서버 `192.168.0.23`에서 Siflower SDK로 ddserver를 빌드했다.
- 보존 환경 파일을 포함한 최종 패키지: `ddserver_0.2-14_mips_siflower-v5-config.ipk` (`12,610`바이트, SHA-256 `5E8C8E41A9018989B4471474699853B19CD70DFC00E8EF55820D43D1E541A308`)
- 최종 Opal 환경값은 `DDSERVER_BULK_READ_SIZE=32768`, `DDSERVER_TRACE_USB=0`이다.
- 배포 전 백업: `/root/d810-deploy-backups/20260728-before-liveview-v5`
- ddserver 배포 전 백업: `/root/d810-deploy-backups/20260728-before-ddserver-v5`
- 스케줄링 보완 전 백업: `/root/d810-deploy-backups/20260728-before-gap-skip`
- LIVE 시작·정지, 640×424 프레임 수신, 서비스 재시작 후 환경값 유지까지 확인했다.
- 측정은 로컬 LAN만 사용했으며 Tailscale SSH 및 외부 포트 공개는 하지 않았다.
