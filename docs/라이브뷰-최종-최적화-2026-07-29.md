# 라이브뷰 최종 최적화

> Nikon D810 · GL.iNet Opal · PTP `0x9203` · WebSocket · Browser UI  
> 최종 기준일: 2026-07-28  
> 문서 정리일: 2026-07-29

## 1. 최종 결론

이 프로젝트의 라이브뷰는 최초 안정 상태 약 `2 fps`에서 출발해, 최종 UI 평균
`55.94 fps`와 전체 지연 평균 `14.22 ms`에 도달했다.

- UI FPS 평균: `55.94 fps`
- UI FPS p10 / p50 / p95 / 최대: `52.7 / 56.5 / 58.1 / 58.5 fps`
- 카메라·브리지 실생산 FPS: `55.72 fps`
- 전체 지연 평균 / p50 / p95 / 최대: `14.22 / 14 / 15 / 15 ms`
- 프레임 사이 request gap 평균: `3.88 ms`
- 시스템 CPU busy: `39.44%`
- Bridge / WebSocket CPU: `14.23% / 8.40%`
- Bridge+WebSocket 프레임당 CPU 비용: 4차 대비 `27.0%` 감소

이 결과는 순간 최대값이 아니라 실제 Opal과 D810, 배포된 브라우저 UI에서
50개 UI 표본과 60초 시스템 측정을 통해 확인한 지속 처리 성능이다.

## 2. 1차부터 5차까지의 변화

| 단계 | 대표 성능 | 핵심 변경 | 해결한 문제 |
| --- | --- | --- | --- |
| 1차 | 안정 약 `2 fps`, 재부팅 후 일시 약 `15 fps` | 셔터식 미리보기 반복을 WebSocket 스트리밍 구조로 전환 | 무선 라이브뷰의 연속 프레임 경로를 최초로 확립 |
| 2차 | 보통 약 `20 fps`, 최대 `26.3 fps` | LIVE 세션 분리, 단일 프레임 생산자, 관측 경로 확립 | 중복 생산과 세션 충돌을 제거하고 최초 목표 15 fps 초과 |
| 3차 | UI 평균 `27.60 fps`, 지연 평균 `28.57 ms` | `0x9203` JPEG를 브리지 메모리에서 WebSocket으로 직접 전달 | 파일 캐시와 소비자 전달 사이의 약 3 fps 손실 제거 |
| 4차 | UI 평균 `28.07 fps`, 지연 평균 `28.04 ms` | JPEG·메타데이터 결합과 재분리, 큰 문자열 복사 제거 | 프레임별 메모리 복사와 재조립 비용 제거 |
| 5차 | UI 평균 `55.94 fps`, 지연 평균 `14.22 ms` | USB 32 KiB 읽기, 버퍼 재사용, 바이너리 헤더, 스케줄링 개선 | USB syscall·파싱·복사·고정 대기 병목 해소 |

초기 안정 `2 fps` 대비 최종 평균 처리량은 약 `28배`가 됐다. 실사용 단계에
진입한 2차의 약 `20 fps`와 비교해도 약 `2.8배`이며, 4차와 5차 사이에서만
UI 평균 FPS가 `99.3%` 증가했다.

## 3. 1차 — 연속 스트리밍 구조 확립

초기 구현은 라이브뷰를 영상 스트림으로 다루지 않고, 촬영 미리보기와 비슷한
방식으로 이미지를 반복 생성했다. 프레임마다 무거운 준비와 종료 과정이
반복되어 지연과 처리 비용이 컸다.

1차에서는 경로를 다음과 같이 바꿨다.

`Nikon D810 → USB/PTP → ddserver → bridge → WebSocket → browser`

첫 안정 결과는 약 `2.0~2.3 fps`였다. 라우터 재부팅 후 약 `15 fps`가
일시적으로 관측됐지만 지속 기준으로 고정하지는 않았다. 이 단계의 핵심
성과는 높은 FPS가 아니라, PTP 라이브뷰 프레임을 무선 브라우저까지 계속
전달하는 기본 구조를 만든 것이다.

## 4. 2차 — 세션과 생산자 안정화

라이브뷰 세션과 일반 카메라 명령 세션이 섞이면 LIVE 상태가 의도하지 않게
종료되거나 여러 루프가 같은 카메라에 접근할 수 있었다. 상태 문제와 성능
문제를 구분하기도 어려웠다.

2차에서는 다음을 해결했다.

- LIVE 유지가 필요한 세션과 일반 명령 세션 분리
- 프레임 생산자를 하나로 제한
- 세션 번호와 로그 보존
- UI 액션, 브리지 명령, PTP 요청, 프레임 생산과 복구 상태의 연계 관측
- 제품 UI를 프레임 소비자 역할로 제한

그 결과 보통 약 `20 fps`, 제품 UI 약 `24 fps`, 측정 최대 `26.3 fps`에
도달했다. 프로젝트 최초 목표였던 `15 fps`를 안정적으로 넘어 실사용 가능한
라이브뷰가 된 단계다.

## 5. 3차 — 메모리 직접 스트림

2차까지 카메라·브리지는 약 `26 fps`를 생산했지만 UI는 약 `23 fps`만
표시했다. 카메라보다 전달 경로에서 약 `3 fps`가 사라지고 있었다.

3차에서는 Nikon `0x9203` 응답의 JPEG를 파일 캐시를 거치는 주 경로 대신
브리지 메모리에서 WebSocket으로 직접 전달했다. 저빈도 파일 캐시는 장애 시
사용할 fallback으로만 남겼다.

| 지표 | 변경 전 | 3차 최종 | 변화 |
| --- | ---: | ---: | ---: |
| UI FPS 평균 | 22.83 | 27.60 | `+20.89%` |
| UI FPS p10 / p50 / p95 | 20.4 / 23.3 / 24.5 | 24.8 / 27.9 / 29.6 | 전 구간 개선 |
| 전체 지연 평균 | 31.37 ms | 28.57 ms | `-8.93%` |
| 전체 지연 p50 | 31 ms | 28 ms | `-3 ms` |
| 전체 지연 p95 | 37 ms | 32 ms | `-5 ms` |

이 단계에서 생산량과 UI 표시량의 간격을 대부분 제거했다.

## 6. 4차 — 프레임 복사와 재조립 제거

3차 직접 스트림에도 프레임별 메모리 비용이 남아 있었다. 브리지는
메타데이터와 JPEG를 하나의 큰 Lua 문자열로 결합했고, WebSocket 서버가
이를 다시 분리한 뒤 WebSocket 패킷 문자열로 재조립했다.

4차에서는 작은 헤더와 JPEG 원본을 별도로 전달하고, 직접 스트림의 JSON
메타데이터도 불필요하게 decode·encode하지 않도록 바꿨다.

| 지표 | 3차 | 4차 | 변화 |
| --- | ---: | ---: | ---: |
| UI FPS 평균 | 27.60 | 28.07 | `+1.70%` |
| UI FPS p10 / p50 / p95 | 24.8 / 27.9 / 29.6 | 25.8 / 28.5 / 30.1 | 개선 |
| 전체 지연 평균 | 28.57 ms | 28.04 ms | `-0.53 ms` |
| 전체 지연 p95 | 32 ms | 31 ms | `-1 ms` |
| WebSocket CPU | 4.64% | 4.62% | 약 `-0.5%` |

직접적인 성능 증가는 작았지만, 프레임 전체 복사를 제거해 5차 USB·바이너리
경로 최적화를 적용할 수 있는 단순한 전달 구조를 만들었다.

## 7. 5차 — USB 읽기와 전체 루프 최적화

4차까지는 D810이 약 30 fps급 프레임만 생성한다고 추정했다. 실제 병목을
구간별로 측정한 결과, 카메라보다 `0x9203` USB 읽기와 요청 루프의 비용이
더 큰 제한이었다.

### 7.1 적용 내용

1. ddserver의 USB 읽기 버퍼 재사용
2. USB endpoint의 512바이트 packet과 애플리케이션 read 요청 크기 분리
3. bulk read 요청을 `32 KiB`로 확대
4. Nikon 384바이트 헤더와 JPEG를 브리지에서 한 번에 분리
5. bridge→WebSocket 메타데이터를 52바이트 바이너리 헤더로 전달
6. JPEG 본문 복사와 캐시 중복 쓰기 축소
7. TCP 지연 옵션 적용
8. 세로·가로 UI의 프레임 파서와 미리보기 경로 통일
9. 직접 스트리밍 중 프레임마다 실행되던 고정 `2 ms` idle sleep 제거

### 7.2 USB bulk 요청 측정

| bulk 요청 | UI FPS 평균 | FPS p50 | 지연 평균 | 지연 p95 | USB reads/frame |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 512 B | 33.02 | 33.6 | 24.12 ms | 26 ms | 약 65회 |
| 4 KiB | 42.52 | 42.9 | 17.48 ms | 19 ms | 약 10회 |
| 16 KiB | 47.59 | 47.6 | 15.00 ms | 15 ms | 4회 |
| 32 KiB | 49.03 | 49.0 | 14.30 ms | 15 ms | 3회 |
| 64 KiB | 49.13 | 49.0 | 14.45 ms | 15 ms | 3회 |

`64 KiB`는 `32 KiB`보다 의미 있는 FPS 이득이 없었고 평균·꼬리 USB 지연은
오히려 나빠졌다. 따라서 같은 처리량에서 더 작은 요청과 안정적인 지연을
보인 `32 KiB`를 최종값으로 선택했다.

### 7.3 마지막 고정 대기 제거

프레임 처리가 끝날 때마다 실행되던 `2 ms` idle sleep을, 활성 LIVE
클라이언트가 존재할 때는 실행하지 않도록 변경했다.

| 지표 | 제거 전 | 제거 후 | 변화 |
| --- | ---: | ---: | ---: |
| request gap 평균 | 5.87 ms | 3.88 ms | `-33.8%` |
| 실생산 FPS | 48.88 | 55.72 | `+14.0%` |
| UI FPS 평균 | 49.39 | 55.94 | `+13.3%` |
| UI 지연 평균 / p95 | 14.20 / 15 ms | 14.22 / 15 ms | 유지 |
| Bridge+WS CPU / FPS | 0.422 | 0.406 | 프레임당 `-3.8%` |

대기 제거로 처리량은 증가했지만 지연과 프레임당 CPU 비용은 악화되지 않았다.

## 8. 4차 대비 최종 개선

| 지표 | 4차 | 5차 최종 | 변화 |
| --- | ---: | ---: | ---: |
| UI FPS 평균 | 28.07 | 55.94 | `+99.3%` |
| UI FPS p10 / p50 / p95 | 25.8 / 28.5 / 30.1 | 52.7 / 56.5 / 58.1 | 전 구간 개선 |
| UI FPS 최대 | 약 30 | 58.5 | 약 `+29 fps` |
| 전체 지연 평균 | 28.04 ms | 14.22 ms | `-49.3%` |
| 전체 지연 p50 / p95 / 최대 | 28 / 31 / 32 ms | 14 / 15 / 15 ms | 꼬리 지연 절반 |
| 시스템 CPU busy | 36.96% | 39.44% | `+2.48 pp` |
| Bridge+WS CPU / FPS | 0.556 | 0.406 | 프레임당 `-27.0%` |

절대 CPU 사용률은 초당 처리 프레임이 거의 두 배가 되면서 증가했다. 그러나
프레임당 비용은 `27.0%` 감소했으므로 비효율 회귀가 아니라 처리량 증가에
따른 정상적인 비용 증가다.

## 9. 최종 구조

```text
Nikon D810
  └─ PTP 0x9203
      └─ ddserver
          ├─ 32 KiB USB bulk read
          └─ reusable receive buffer
              └─ d810bridge
                  ├─ Nikon 384-byte header 분리
                  ├─ JPEG memory stream
                  └─ 52-byte binary metadata
                      └─ WebSocket
                          ├─ latest-frame delivery
                          └─ no fixed 2 ms idle during active LIVE
                              └─ portrait / landscape browser UI
```

저빈도 파일 캐시는 복구용 fallback으로 유지하며, 정상 LIVE 경로에는
프레임 파일 쓰기와 재읽기를 요구하지 않는다.

## 10. 최종 판정과 변경 규칙

최종 라이브뷰는 **56 fps급 지속 처리**, **60 fps급 카메라 출력에 근접한
브라우저 전달**, **15 ms 이하의 안정적인 꼬리 지연**을 달성했다.

이 버전을 D810 라이브뷰의 최종 동결 기준선으로 사용한다. 이후 라이브뷰
경로를 변경할 때는 다음 조건으로 같은 전후 측정을 수행한다.

- UI FPS 평균과 p10 / p50 / p95
- 카메라·브리지 실생산 FPS
- 전체 지연 평균과 p50 / p95 / 최대
- request gap
- 시스템·Bridge·WebSocket CPU
- LIVE 시작·정지·재시작 및 촬영 후 복귀

성능이나 안정성이 이 기준보다 회귀하면 변경을 적용하지 않는다.
