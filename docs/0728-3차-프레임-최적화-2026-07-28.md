# 3차 프레임 최적화 — 2026-07-28

- Status: implemented, deployed, and measured on the real Opal
- Final path: Nikon `0x9203` → bridge memory stream → WebSocket → browser
- Total latency average: `31.37 → 28.57 ms` (`-8.93%`)
- Total latency p95: `37 → 32 ms` (`-13.51%`)
- UI FPS average: `22.83 → 27.60 fps` (`+20.89%`)

## Scope

- Device: GL.iNet Opal on the local LAN (`192.168.8.1`)
- Camera/UI: Nikon D810, deployed v21 UI
- No Tailscale SSH or external exposure
- The browser stayed connected and rendered the WebSocket live view.
- No production files were changed for this baseline.

## Method

- A single Lua sampler ran locally on Opal to avoid repeated SSH sampling overhead.
- Paired 30-second idle and live-view windows used the same 10 ms sampler.
- A separate 60-second live window confirmed the longer-run system result.
- `/proc/stat` supplied system CPU, forks, and context switches.
- `/proc/<pid>/stat` supplied bridge and WebSocket CPU ticks.
- `/tmp/d810-live-v21.meta` supplied unique frame IDs and capture/cache timing.
- The deployed browser UI supplied 20 FPS/latency-meter samples over 10 seconds.

Sampler: `deploy/scripts/opal-liveview-baseline.lua`

## Finding

`frame-refresh-v21` was not running during the measurement, and the direct
stream port had accepted no clients. The active flow is:

1. the bridge captures a JPEG;
2. the bridge writes the JPEG and metadata under `/tmp`;
3. `d810ws.lua` polls the metadata every 33 ms;
4. it reopens the JPEG and sends it to the browser.

The next optimization target is therefore direct in-memory bridge-to-WebSocket
delivery with the file path retained only as a fallback. This should be measured
against the CPU, delivered FPS, frame gap, and new end-to-end latency baseline
above.

## Direct-stream optimization

The bridge now sends each `0x9203` JPEG and its frame metadata over the existing
local port `8190`. The WebSocket daemon consumes that framed stream directly.
The old frame-file reader remains as a connection fallback, while the bridge
updates `/tmp` at a low frequency for snapshot and recovery consumers.

The first direct-stream test exposed an unused-code defect: `read_exact()` read
the JPEG one byte per syscall, limiting the UI to about 2 fps and back-pressuring
the bridge. It was corrected to request the full remaining payload. The final
deployment passed stop/start recovery and direct-stream reconnection checks.

## Verified total-latency A/B

The same deployed UI was used for both backends with `e2e=total`. This makes
the latency meter use `Date.now() - startedAt` after the JPEG image `load`
event, covering the complete `0x9203 request start → browser image load`
interval. Each phase sampled 30 one-second UI windows.

| Metric | File-polling backend | Direct-stream backend | Change |
| --- | ---: | ---: | ---: |
| UI FPS average | 22.83 | 27.60 | +20.89% |
| UI FPS p10 | 20.4 | 24.8 | +21.57% |
| UI FPS p50 | 23.3 | 27.9 | +19.74% |
| UI FPS p95 | 24.5 | 29.6 | +20.82% |
| Total latency average | 31.37 ms | 28.57 ms | -2.80 ms / -8.93% |
| Total latency p50 | 31 ms | 28 ms | -3 ms / -9.68% |
| Total latency p95 | 37 ms | 32 ms | -5 ms / -13.51% |
| Total latency maximum | 37 ms | 34 ms | -3 ms / -8.11% |

An earlier `captureDoneAt` meter run produced values indistinguishable from the
capture-duration fallback and was therefore not accepted as a complete
delivery measurement. The table above supersedes it with the explicitly
verified total pipeline timestamp.

The file-polling path often skipped intermediate frames instead of holding a
delivered frame for the full polling interval. That explains why the FPS gain
is much larger than the average total-latency reduction.
