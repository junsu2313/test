# 출사 환경 라이브뷰 안정화 조사 및 해결 기록

작성일: 2026-08-01  
대상: Opal 로컬 카메라 시스템 — ddserver, 브리지, WebSocket, 웹 UI, Android 앱

## 1. 문제 발견

인터넷이 연결된 개발 환경에서는 웹 UI와 앱 모두 기본적인 카메라 제어가 동작했다. 그러나 인터넷을 끊은 출사 환경에서 다음 문제가 나타났다.

- 셔터와 일부 카메라 명령은 동작하지만 라이브뷰 프레임이 들어오지 않았다.
- `live-off`를 눌러도 화면과 백그라운드 프레임 생산이 완전히 멈추지 않았다.
- STOP 이후에도 프레임 생산자가 남아 다음 LIVE 시작을 방해할 가능성이 있었다.
- WebSocket, 브리지, ddserver 중 하나가 재시작되면 세션은 살아 있는 것처럼 보이지만 실제 프레임은 멈췄다.
- AF 직후 셔터를 빠르게 누르면 카메라가 PTP `0x2019(Device Busy)`를 반환했다.
- 여러 차례 ddserver를 강제종료하자 procd가 서비스를 더 이상 재시작하지 않았다.

초기에는 인터넷 연결 여부가 직접 원인인지 의심했다. 하지만 로컬망의 SSH와 웹 접속은 유지됐고, 인터넷이 없어도 정상 LIVE·AF·셔터·STOP이 동작하는 순간이 확인됐다. 따라서 인터넷은 직접 원인이 아니라, 연결 변화와 재접속이라는 예외 경로를 발생시킨 조건으로 분류했다.

## 2. 방법 탐색

### 2.1 정상 경로와 장애 경로 분리

먼저 카메라를 정상 상태로 되돌린 뒤 다음 순서로 확인했다.

1. LIVE 시작 후 실제 프레임 ID가 증가하는지 확인
2. WebSocket 단일·복수 접속에서 JPEG와 메타데이터 수신 확인
3. LIVE 중 AF와 실제 셔터 확인
4. LIVE 종료 후 프레임 ID 정지와 임시 상태 파일 제거 확인
5. 이후 WebSocket, 브리지, ddserver를 각각 강제종료해 복구 여부 확인

단순히 HTTP 응답이 `ok`인지 확인하는 것만으로는 부족했다. 카메라가 감지되더라도 프레임 생산자가 멈출 수 있기 때문이다. 그래서 최종 검증 기준을 다음처럼 강화했다.

- `liveView=true`
- `backendState=live`
- `frameAgeMs < 2000`
- 연속 상태 조회 사이에서 `frameId` 증가
- 장애 전후 동일한 세션 ID 유지
- STOP 후 `cameraStopConfirmed=true`

### 2.2 로그와 프로세스 상태 대조

웹·앱의 응답만 보지 않고 다음 정보를 함께 비교했다.

- 브리지 영구 세션 로그
- ddserver syslog의 `liveview9203` 처리 로그
- `/tmp`의 LIVE 의도·프레임 메타데이터 파일
- ddserver, 브리지, WebSocket 프로세스 목록
- procd의 서비스 상태와 respawn 설정
- 프레임 ID, 프레임 나이, 실패 횟수

이 비교를 통해 “카메라가 감지된다”와 “라이브뷰 프레임이 계속 생성된다”가 서로 다른 상태라는 점을 확인했다.

## 3. 원인 확정

### 3.1 프레임 생산자 종료 경쟁

웹 UI와 앱의 STOP 경로가 서버에 `LIVE_STOP`을 요청하기 전에 각자의 로컬 재연결·프레임 루프를 먼저 차단하지 않았다. 서버가 카메라를 멈추는 순간 클라이언트가 다시 LIVE를 요청할 수 있었다.

또한 서버 쪽에서도 카메라 STOP 확인이 실패하면 로컬 생산자 종료까지 함께 실패하는 구조가 있었다. 이 때문에 카메라 상태와 무관하게 반드시 로컬 생산자를 fence해야 했다.

### 3.2 ddserver USB 패킷 파서의 포인터 오류

라이브뷰 응답 버퍼가 커져 `resize()`가 발생하면 버퍼의 메모리 주소가 바뀔 수 있다. 기존 코드는 재할당 전의 `PtpPacket*` 포인터를 계속 사용했다. 그 결과 응답 길이를 잘못 읽어 다음 패킷을 비정상 길이로 해석할 수 있었다.

이 문제는 기존 오팔에 설치된 구형 ddserver 바이너리에는 남아 있었고, 소스 수정본에는 반영되어 있었지만 실제 바이너리 배포가 필요했다.

### 3.3 자동 복구 중 레거시 fallback 고착

ddserver가 재기동 중일 때 브리지는 영구 소켓 연결에 실패하면 레거시 `d810d.lua` 방식으로 전환했다. 이 전환은 일시적인 procd 재기동 지연을 `liveview_start_failed`로 바꿨고, 이후에도 영구 소켓 재접속을 시도하지 않는 고착 상태를 만들었다.

즉, 복구 중에는 실패하더라도 다음 영구 연결 재시도가 가능해야 하는데, 레거시 fallback이 복구 경로를 막고 있었다.

### 3.4 LIVE 의도 소실

재접속 함수가 실패하는 과정에서 `live_view_active`와 `session_mode_live`를 먼저 지웠다. 연결이 실패하면 LIVE를 복원해야 하는데, 복원 기준 자체가 사라지는 문제가 있었다.

그래서 오래된 세션 메타데이터가 아니라 명시적인 클라이언트 LIVE 요청 파일만 복구의 권위 있는 기준으로 사용하고, 복구 실패 시에도 그 의도를 보존하도록 변경했다.

### 3.5 AF 완료 전 셔터 경쟁

AF 명령은 응답을 반환했지만 카메라 내부 포커스 처리가 끝나기 전일 수 있었다. 바로 이어진 셔터가 `0x2019(Device Busy)`를 받았다.

기존 오류 분류도 이 응답을 `camera_missing`으로 표시해 원인을 숨기고 있었다.

### 3.6 procd 재시도 한도 소진

ddserver init에는 procd 기본 재시도 정책이 적용되어 있었다. 짧은 시간에 여러 번 프로세스를 강제종료하자 `6 crashes`로 판단해 서비스를 영구 정지시켰다.

이 상태에서는 브리지 로직이 아무리 재접속을 시도해도 ddserver 자체가 없으므로 복구할 수 없었다.

## 4. 해결 방법

### 4.1 STOP과 생산자 소유권 정리

- 웹 UI와 Android 앱에서 STOP 전에 로컬 재연결 루프를 차단
- 서버는 카메라 STOP 확인 성공 여부와 관계없이 로컬 생산자를 항상 종료
- 새 ddserver 연결을 통해 STOP을 한 번 재시도
- 명시적인 LIVE 요청이 없으면 세션 메타데이터만으로 LIVE를 되살리지 않도록 제한

### 4.2 ddserver 수정 및 재빌드

- USB 버퍼 재할당 뒤 모든 패킷 포인터를 새 버퍼 기준으로 갱신
- PTP 패킷 길이를 명시적으로 little-endian으로 해석
- 비정상적으로 작거나 큰 패킷 길이 거부
- 라이브뷰 USB bulk read 크기와 처리 시간을 로그로 확인 가능하게 구성
- Siflower SDK로 MIPS 바이너리를 다시 빌드

최종 패키지는 `ddserver 0.2-15`이며, 오팔에서 실행 중인 바이너리 해시와 빌드 산출물 해시가 일치하는 것을 확인했다.

### 4.3 영구 연결 복구 강화

- LIVE 의도가 있는 동안 자동 재접속은 영구 ddserver 연결만 시도
- procd 재기동 지연 중 레거시 fallback으로 내려가지 않도록 차단
- `transport_error`뿐 아니라 `liveview_start_failed`도 재복구 대상에 포함
- `ensure_connected()`도 LIVE 의도를 보존하는 `recover_transport()` 경로를 사용
- 재접속 성공 시 동일 세션에서 LIVE를 복원하고 프레임 생산을 재개

### 4.4 AF와 오류 분류 수정

- AF 명령 후 카메라가 `DeviceReady`가 될 때까지 대기
- AF 직후 셔터가 Busy 경쟁을 일으키지 않도록 처리
- PTP `Device Busy`는 `camera_busy`로 보고
- 세션 손실은 `transport_error`로 보고
- 단순 PTP 카메라 오류는 `camera_error`로 보고

### 4.5 ddserver 서비스 감독 수정

procd 설정을 다음과 같이 변경했다.

```sh
procd_set_param respawn 3600 5 -1
```

이를 통해 반복 장애 후에도 ddserver가 자동 재시작을 계속 시도한다. 실제 오팔의 `ubus` 서비스 정보에서도 `retry: -1`을 확인했다.

### 4.6 검증 도구 수정

기존 스트레스 시험은 `cameraDetected=true`만 확인해 프레임이 멈춘 상태를 통과시킬 수 있었다. 다음 기준으로 강화했다.

- 최신 프레임 나이 검사
- LIVE 상태와 backend 상태 검사
- 연속 조회 사이 frameId 증가 검사
- 장애 전후 세션 ID 유지 검사
- WebSocket, 브리지, ddserver 장애를 각각 독립적으로 검증

## 5. 해결 확인

배터리 교체와 카메라 전원 재부팅 후 다음 결과를 얻었다.

### 정상 경로

- LIVE 프레임 생성: 통과
- JPEG 및 메타데이터 수신: 통과
- 다중 WebSocket 접속: 통과
- AF: 통과
- AF 직후 셔터: 통과
- 실제 셔터: 통과
- STOP: `cameraStopConfirmed=true`
- STOP 후 프레임 생산자 및 임시 파일 제거: 통과

### 장애 경로

- WebSocket 강제종료 후 복구: 통과
- 브리지 강제종료 후 복구: 통과
- ddserver 강제종료 후 복구: 통과
- 동일 세션 유지: 통과
- 복구 후 신선한 frameId 증가: 통과
- 최종 종합시험: 9/9 통과

최종 ddserver 장애시험에서는 ddserver 종료 후에도 같은 세션에서 `frameId 2587 → 2798`로 증가했고, 프레임 나이는 61~66ms, 실패 횟수는 0이었다. 마지막 STOP도 카메라 확인을 포함해 정상 처리됐다.

## 6. 결론

인터넷 단절은 직접적인 라이브뷰 원인이 아니었다. 인터넷이 연결된 개발 환경에서는 정상 연결 상태가 유지되어 종료·재접속·서비스 재시작 경쟁 조건이 거의 발생하지 않았다. 오프라인 출사 환경에서 이 예외 경로가 처음 강하게 실행되면서 잠복 버그가 드러났다.

이번 해결의 핵심은 특정 오류 하나를 우회한 것이 아니라, 다음 세 가지를 명확히 한 것이다.

1. LIVE 생산자의 단일 소유권
2. 장애 중에도 보존되는 명시적 LIVE 의도
3. 실제 프레임 증가를 기준으로 한 복구 검증

현재 시스템은 인터넷 연결 없이도 로컬망에서 웹 UI와 앱으로 카메라를 제어할 수 있으며, WebSocket·브리지·ddserver 장애 후에도 자동 복구할 수 있는 상태로 실기 검증을 완료했다.
